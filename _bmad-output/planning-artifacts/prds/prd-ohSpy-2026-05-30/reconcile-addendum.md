# Reconciliation — addendum.md vs PRD

## Summary

The PRD does a strong job of carrying forward the addendum's PRD-relevant capability commitments — the named "Slow responses" and "Full-screen repaints" root causes are each addressed by name (NFR-P2 timeout discipline, FR-100 incremental SCPD, FR-101 virtualisation, NFR-P5 keyed updates), and the five Design Objectives are all reflected in the §5 NFRs. The five reference FR IDs (FR-047, FR-044, FR-051, FR-049, FR-048, FR-004) are preserved verbatim with original intent intact. The principal residual risks are: (a) two named "Slow responses" sub-causes are only partially mitigated (event-pump one-by-one parsing — FR-Subscription §4.10 acknowledges malformed-NOTIFY tolerance but does not commit to pipelined/parallel processing); (b) two named "Full-screen repaints" sub-causes (TreeView InsertSorted weak tracking and device-removal subtree redraw) are folded under generic NFR-P5/NFR-UI3 language rather than called out as specific repaint hazards to verify; (c) several "Open gaps" in the addendum are dropped silently rather than explicitly decided in / out; (d) the "Carry forward" list's diagnostic-format commitment (rolling JSON-lines + in-memory ring) is partially under-specified — the JSON-lines format itself is not a PRD commitment.

## Gaps (severity-ranked)

- **high** Event-pump one-by-one parsing not addressed as a named fix (addendum "Root causes / Slow responses" §3 / PRD §4.10 + §5) — Addendum names "Event pump processes NOTIFY one-by-one; a bad NOTIFY can block the parser" as one of three root causes of slow responses. PRD §4.10 Feature-specific NFRs says "Notification processing MUST tolerate one malformed NOTIFY without blocking subsequent events" — this covers the *fail-safe* dimension but not the *throughput* dimension (one-by-one serial processing remains an implicit possibility). No NFR explicitly requires pipelined / non-serial NOTIFY processing per subscription, despite the addendum identifying serial processing itself as a slow-response root cause. *Fix:* Add a sentence to §4.10 Feature-specific NFRs (or a new FR-104) committing that per-subscription NOTIFY processing MUST NOT serialise such that one slow parse blocks subsequent notifications beyond the no-blocking budget — i.e., the bounded `Channel<EventNotification>` is drained off the receive path.

- **high** TreeView "weak item-level tracking / InsertSorted remove+insert" repaint hazard not called out (addendum "Root causes / Full-screen repaints" §2 / PRD §4.3 + NFR-P5) — Addendum specifically names "WinUI TreeView has weak item-level tracking — InsertSorted() (remove + insert) on label refresh may trigger a subtree redraw". PRD §4.3 Feature-specific NFRs and NFR-P5 both demand "keyed, identity-tracked collection updates" generally, and FR-054 requires node identity preservation across label-driven row migrations — which addresses the *intent* — but neither explicitly forbids the remove+insert pattern for re-sorting nor names subtree redraw as a tested-against repaint hazard. *Fix:* Strengthen FR-054 (or §4.3 NFRs) to forbid remove+insert as a sort-maintenance mechanism (require in-place move / index-shift) and add an acceptance criterion that a label change MUST NOT redraw the device's expanded subtree.

- **medium** Device-removal subtree redraw hazard not called out (addendum "Root causes / Full-screen repaints" §4 / PRD §4.1 FR-008 + NFR-P5) — Addendum names "Device removal on byebye may cause expanded subtree to redraw" as a fourth root cause. PRD has FR-008 (byebye removal) and NFR-P5 (keyed updates), but no specific NFR/FR forbids a subtree redraw cascade when a sibling device is removed. *Fix:* Add a consequence-row under FR-008 (or NFR-P5) stating removal of one top-level device MUST NOT cause repaint of sibling devices' expanded subtrees.

- **medium** "Open gaps" decisions silently dropped (addendum "Open gaps" / PRD §7 + §8.2 + §10) — Addendum lists seven explicit "needs to decide on" gaps. PRD's decision status:
  - HTTP timeout override per request — DECIDED IN (NFR-P2). Good.
  - Virtual scroll on SSDP log — DECIDED IN (FR-101). Good.
  - Lazy/streaming SCPD parse — DECIDED IN (FR-100). Good.
  - Tooltip on tree rows (Tier 2 deferred) — DECIDED OUT (§8.2 "Hover tooltip on tree rows … deferred"). Good.
  - Automatic device-name refresh on re-announce — PARTIAL DECISION (§8.2 "Automatic device-name refresh on re-announce *beyond* the FR-054 sort/migration behaviour" — covered, but only by inference: FR-054 implicitly accepts label updates that migrate the row, no explicit "label updates in-place if no migration"). Acceptable but worth a line.
  - SSDP message filtering in the log view — DECIDED OUT (§7 Non-Goals implicit, §8.2 explicit, §10 OQ#2). Good.
  - Cross-session state (window layout, last selection) — DECIDED OUT (§7 Non-Goals explicit). Good.
  No genuinely-dropped gaps — but the "automatic device-name refresh" decision is implicit-via-FR-054 rather than explicit; an L&L reader matching addendum-to-PRD will have to do work. *Fix:* Add a single line to §8.2 confirming "label updates from re-announce update the row in place per FR-054 — no separate rebadge affordance" (which the existing wording almost says — tighten it).

- **medium** "Rolling JSON-lines diagnostic file" format commitment not in PRD (addendum "Carry forward" / PRD FR-040) — Addendum's Carry Forward explicitly names "Rolling JSON-lines diagnostic file + in-memory ring" as a working pattern to land unchanged. PRD FR-040 commits to rolling and bounded, FR-041 commits to in-memory ring, but neither commits to **JSON-lines** specifically. JSON-lines is borderline — it's a format/serialization decision that could be argued as architecture — but the brief's "machine-readable diagnostic trail" framing and downstream tooling expectations make the format a capability concern (post-mortem parseability). *Fix:* Either add a line to FR-040 ("rolling log file rendered as one structured record per line — JSON Lines recommended; final format ratified in architecture phase") OR explicitly note in the Assumptions Index that the on-disk format is an architecture decision deferred.

- **low** "No UI thread blocking as enforced invariant — verified in tests if possible" — partial commitment (addendum "Design objectives" §5 / PRD NFR-P3) — Addendum says "enforced invariant — verified in tests if possible". PRD NFR-P3 says "verified by static analysis or by integration tests where feasible". This is faithful to the qualified "if possible" / "where feasible" hedge. Listed as low because the hedge is preserved; mention only for completeness. *Fix:* None required; if anything, tighten by naming Roslyn analyzer / banned-API list as the preferred mechanism in architecture phase.

- **low** Discovery MX value not surfaced (addendum architecture shape / PRD FR-004 + SC-001) — Addendum mentions "M-SEARCH on startup with MX=3s"; PRD SC-001 cites "5 s MX" as the budget. Numbers don't line up (3 s vs 5 s). This is borderline architecture but the discrepancy is visible in the PRD and worth noting — likely just an inherited number from UpnpSpy `plan.md` that the addendum either updated or the PRD rounded. *Fix:* Reconcile in architecture phase; flag for confirmation.

- **low** Reference to `plan.md` performance budgets not fully threaded (addendum "Reference artifacts" / PRD §6) — Addendum cites "performance budgets (5s startup discovery, 2s cold SCPD expansion, 100ms warm expansion when eager-fetched)". PRD §6 carries SC-001 (~7 s total = 5 s MX + 2 s eager fetch), Warm SCPD ≤100 ms, Cold large-SCPD ≤2 s — all present. *Fix:* None; verified preserved.

## Out-of-scope by design (correctly absent — tech detail for architecture phase)

- **Addendum "Tech stack" §** — WinUI 3 / WindowsAppSDK 1.5 / CommunityToolkit.Mvvm / .NET 7 / MSIX / Microsoft.Extensions DI / xUnit+Moq+FluentAssertions / x64+ARM64 publish profiles. All architecture; correctly absent from PRD. PRD's NFR-UI1 references "WinUI 3 design guidelines" but explicitly flags (Assumptions Index, §11) that this is "an architecture decision in the addendum; this PRD is consistent with it but does not by itself ratify it" — exactly right.
- **Addendum "Architecture shape" §** — Two-project App/Core split; two bound sockets per NIC (multicast :1900 + ephemeral); bounded `Channel` capacity 4096; SemaphoreSlim(8) gate concrete number; SOAP POST shape; hand-rolled HttpRequestReader; per-subscription Channel capacity 1024. The *capacity* numbers (8 fetch concurrency, 10K SSDP cap, 5K subscription event cap, 5K diagnostic ring cap) are preserved in PRD §6 — appropriate, because they're capability-level budgets. The lower-level transport/parser specifics (two sockets, hand-rolled HttpRequestReader, exact Channel capacities for internal buffers) are correctly absent.
- **Addendum "Tech stack — Tests"** — xUnit + Moq + FluentAssertions — architecture; correctly absent.

## Notable preservation

- **All five Design Objectives reflected in NFRs:** virtualised scrolling → FR-101 + NFR-P1; per-request HTTP timeout → NFR-P2; streaming SCPD parse → FR-100 + NFR-P4; keyed collection updates → NFR-P5 + FR-054; no UI thread blocking → NFR-P3.
- **Both named complaints traced as Success Metrics:** SM-2 explicitly names "the two UpnpSpy complaints" and binds them to FR-101 + NFR-P1/P5 (repaints) and NFR-P2 (timeouts).
- **All five referenced FR IDs preserved verbatim with original intent:** FR-047 (hide-until-loaded), FR-044 (chevron via "Loading…" placeholder), FR-051 (secondary detail line), FR-049 (TcpListener — no URL ACL, no Admin — preserved with explicit consequences), FR-048 (single adapter, radio-list switch), FR-004 (M-SEARCH `ST: upnp:rootdevice`). FR-049's "no HttpListener, no netsh, no Admin" trifecta — flagged in addendum's "Carry forward" as a huge ergonomic win — is preserved as testable consequences. Excellent.
- **Async-throughout enforced as NFR-P3** with explicit `.Result` / `.Wait()` ban — matches addendum's "Async/await throughout; no `.Result` / `.Wait()`" carry-forward.
- **Bounded fan-out preserved as NFR-P6** with the 8-concurrent target — matches addendum's "Bounded concurrency on eager fetch".
- **Sorted, keyed tree insertion preserved as FR-054** with case-insensitive primary + UUID secondary key — matches addendum's `(FriendlyName, Uuid)` keying.
- **Registry/VM separation preserved as the FR-047 + FR-053 + Glossary distinction** between registry and visible tree — addendum's "decoupled discovery state from UI state" is explicitly architected into the capability vocabulary.
- **Mismatched-root backstop (FR-053 layer c + FR-043 mismatch clause)** is a genuine elaboration over the addendum, not a regression — addendum mentions three-layer enforcement intent; PRD spells out all three layers with the backstop as the third.
