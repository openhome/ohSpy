## What went well

- **The diagnostics viewer paid for itself on its FIRST smoke.** Before it could even be judged as a feature, opening `View → Diagnostics` against the live network immediately exposed a genuine Epic-2 defect: `SsdpParser` was logging every ordinary M-SEARCH *request* as `Warning "ssdp parse failed"` with no reason — flooding the log and mislabelling normal traffic as failures. Fixed cleanly (commit `884ab84`): M-SEARCH → `Verbose Ssdp.SearchObserved`; genuine parse failures now carry an `ErrorText` reason. A diagnostics tool that finds bugs the moment it ships is the strongest possible validation of the tool.
- **Q1 was a real product decision, made mid-story and made well.** The epic prose and the architecture (D8) pulled in opposite directions — D8's `MinSeverity` is an emitter gate (entries below it never allocate, AC-8.7), the epic AC's `MinSeverity` is a pure view filter that "MUST NOT mutate the ring." The Project Lead resolved it by **coupling both** behind one operator control via a new runtime-mutable `IDiagnosticLevelGate` (DiagSeverity ordinal via `Volatile.Read/Write`, seeded from `DiagnosticOptions.MinSeverity`, zero-alloc fast-path preserved and re-verified with a raise-at-runtime <4-bytes/call test). Flipping to Verbose genuinely turns the firehose on; raising it turns it off. That is a better product than either source spec described.
- **`create-story` reconciliation caught stale epic prose again — in BOTH stories.** The epic said each story "creates / adds to" the View menu as a complete shape; in reality 5.2 already built the menu, 5.1 added only `Diagnostics`, and 5.3 added only `Rescan`. 5.3's reconciliation went further and corrected the architecture map itself (`DiscoveryService.RescanAsync → transport` is impossible post-A23; `DeviceRegistry.PruneNonResponders` doesn't exist). Reconcile-against-shipped-code keeps earning its keep — five separate stale statements corrected before dev in 5.3 alone, zero rework.
- **Epic-4 groundwork made 5.3 nearly free.** 5.3 added no ctor param, no DI registration, no launcher seam — `RescanCommand` is just a member on the already-singleton `ShellViewModel`. It reused the A23 scope-owned transport (a one-line `AdapterScope.SendMSearchAsync` pass-through to the scope-owned token) and mirrored the 5.2 `Clear()` cascade for the new `PruneNotSeenSince`. The prune rule is a pure function of the shipped `LastSeenUtc` liveness model — no new per-entry bookkeeping. Contrast 5.2, the most interconnected story in the project; 5.3 is the cheapest.
- **The exact-set `DiagCategories` pin did its job twice.** Both new constants (`Ssdp.SearchObserved` in 5.1's fix, `Adapter.Rescan` in 5.3) forced the constant + the `expectedNames` exact-set test + architecture D8 to change together, in one PR, flagged to the reviewer as intentional. The pinned set makes "did the diagnostic surface drift?" a compile/test failure, not a guess.

## What didn't — the headline lesson

**The 5.1 viewer was built, built clean (537 green), and was still functionally dead on screen — both the severity colour and the view filter — because `ItemsRepeater` leaves a realized row's `DataContext` null.** Review (Sonnet) caught both as P1: a classic `{Binding Entry.Severity}` converter never fired (DataContext null → default foreground on every row), and the per-row `Visibility` filter read `fe.DataContext is DiagnosticRow`, always false. This is the **same structural class as every prior epic's UI bug** — a WinUI rendering reality the headless Core suite cannot see — and it is exactly why smoke-per-ui-story and now adversarial review on the App XAML both stay first-class gates.

The fix produced a **new durable gotcha worth flagging loudly:** the reviewer's reflexive suggestion — switch to `x:Bind … Converter={StaticResource …}` — **does not compile when the XAML root is a `Window`.** WinUI 3 `Window` is not a `FrameworkElement`, so the generated `StaticResource` lookup fails (CS1503 in `DiagnosticsWindow.g.cs`). The actual fix was to set each realized row's `DataContext = ViewModel.Entries[args.Index]` in `OnRowPrepared` and use classic `{Binding}` (and index-based row reads for the filter). So the durable knowledge is two-layered: (1) `ItemsRepeater` + `x:DataType` leaves realized `DataContext` null — bind by index in `OnRowPrepared`; (2) `x:Bind` + a `{StaticResource}` converter is **not** the escape hatch under a `Window` root.

A smaller, well-handled wrinkle in 5.3: the switch-wins race surfaced an `ObjectDisposedException` (reading `_adapterCts.Token` on a concurrently-disposing CTS) instead of the `OperationCanceledException` the "abandoned — switch in progress" path expects — so the operator would have seen the wrong "rescan failed" diagnostic. Review caught it; the fix wraps the pass-through to translate ODE→OCE, with a regression test. Correctness was never at risk (the prune never ran in either case), only the diagnostic message — but on an operator-tooling epic, the diagnostic message *is* the product.

## Key takeaways

1. **A diagnostics tool's first smoke is a test of the whole codebase, not just the tool.** 5.1 found and fixed a real Epic-2 SSDP-logging defect (`884ab84`) the instant it rendered — the best validation operator tooling can earn. Ship the lens, then look through it.
2. **A green build is still invisible until smoke + review see the screen.** 5.1 compiled with 537 green tests and was functionally dead (no severity colour, no filter) because `ItemsRepeater` leaves realized `DataContext` null — the recurring "headless Core can't see WinUI rendering" class. Adversarial review on the App XAML + the mandated large-stream smoke both did their jobs.
3. **The new durable gotcha: under a `Window` root, `x:Bind`+`{StaticResource}` converter won't compile; bind by index in `OnRowPrepared`.** The obvious WinUI fix is a dead end here — worth recording so the next Window-rooted `ItemsRepeater` view doesn't relearn it.
4. **Epic-4 groundwork made the last feature nearly free.** 5.3 added no ctor/DI/launcher — just a command on the singleton `ShellViewModel`, an A23 transport pass-through, and a `Clear()`-shaped prune. The most interconnected story (5.2) paid for the cheapest one (5.3).
5. **This was the last feature epic, and the methodology held to the end.** create-story reconciliation (5 stale statements corrected in 5.3), pinned-set discipline (two constants synced cleanly), Action H (both async paths guarded), and smoke-per-ui-story all fired as designed. Epic 6 is verification, not construction.
