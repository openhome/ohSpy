## Part 0 — Why this retro is different

ohSpy had a dual purpose from day one, and the closeout has to be read through both lenses:

1. **A real tool.** A native Windows WinUI 3 UPnP inspector for Linn engineers — the supported successor to Intel's discontinued Device Spy. Non-negotiable quality bars: **reliability, performance, UI polish.**
2. **An evaluation / Lunch-&-Learn deliverable.** Does **Claude Code + BMad spec-driven development** produce a better result than the prior `C:\work\UpnpSpy` (same problem, built with Claude + spec-kit)? The *journey* — brief → PRD → architecture → epics → fresh-context create-story → dev-story → Sonnet code-review → manual smoke per story → v1.0.0 — **is** the pitch. The Project Lead stated the L&L outcome may matter more than the tool.

So this document does the standard Epic 6 review, then steps back to the whole-project arc, the methodology's strengths and blind spots, the **test-vs-reality gap as the headline durable lesson**, and a reasoned verdict on the L&L question.

### 1.1 What went well in Epic 6

- **Verification-as-a-story worked.** 6.1 turned "smoke-per-ui-story" into a first-class, reportable deliverable with a PASS/FAIL/N/A matrix and a stale-AC reconciliation. It caught two real polish defects (D1/D2) the eye sees and tests don't — and the verification report is itself an L&L artefact.
- **The headless soak harness is a genuinely clever boundary solution.** It exercises the real Core VM + service stack under sustained, larger-than-life load without touching WinUI — respecting the Pattern-2 boundary while still proving no-leak / no-stall. The `PumpingUiDispatcher` closed the one gap the convenience dispatchers leave (you cannot measure a UI-thread stall with a dispatcher that runs inline). The 1-hr run at release: 0 crashes, 0 UI-thread stalls > 1 s, max dispatch gap 177 ms, memory plateaued ~120 MB WS with no leak.
- **The review kept doing real work to the very last epic.** 6.2's CHANGES-REQUESTED verdict found the hardcoded 8-hr assertions — the trivially-passing trap the team has chased since Epic 1's A18 chaos-hook silent no-op. The pattern recognition compounded: the reviewer *went looking* for it.
- **The corrective block closed cleanly on its own merits.** 2-11 and 2-12 each: authored their own PRD FR + Architecture amendment, shipped with a green automated suite, passed a fresh-context Sonnet review, AND passed a first-class live smoke (no-byebye expiry; physical cross-network move). The "corrective work on a closed epic stays in Epic 2, epic-status not re-opened" precedent (set by 2-10) held a third and fourth time.
- **Chaos-hook discipline held for the entire project.** 60 commits before release, 0 `--no-verify` bypasses. The pre-commit chaos hook substituted for CI exactly as Decision 13 intended.

### 1.2 What didn't — the Epic-6 headline lesson: the field found what no gate did

Epic 6 was supposed to be *verification-only — no new FRs*. It delivered two new FRs (FR-056, FR-057) anyway, because **the two most important defects of the whole back half of the project were invisible to every gate the project had and only appeared in the real world after install:**

- **No inferred-byebye expiry.** A device powered off without sending an SSDP `byebye` lingered in the tree forever. The whole discovery suite — and the soak farm — used devices that either stayed alive or sent byebye. Nothing in 574 tests modelled "device vanishes silently," because that is a property of *real hardware and real power switches*, not of a fake. Fixed by 2-11 (FR-056, A33).
- **No network-change detection.** Move the laptop from the office to home and the office's devices stayed on screen — the app never noticed the host's network changed. No unit test moves a machine between two physical networks. Fixed by 2-12 (FR-057, A34).

Both were caught by the Project Lead *using the tool for real* — which is exactly what a verification-only epic and a clean-machine install dry-run are for, and exactly what no green suite could have surfaced. This is the test-vs-reality gap (Part 3) in its purest form: the suite was as green as it had ever been (574/2) and the tool still had two real, user-visible reliability holes.

### 1.3 The install-blocker saga (a two-layer red herring)

The clean-machine install was the single highest-risk item for the L&L "drop the installer on a fresh box and run it" narrative, and it bit in two distinct layers:

1. **The named, anticipated bug (the red herring that everyone watched).** `Program.cs` called the framework-dependent `Bootstrap.TryInitialize(2.1.3)` while the csproj declared `WindowsAppSDKSelfContained=true` — mutually exclusive. A clean box with no installed WinAppRuntime died at `0x80670016`. This had been logged since Epic 2, flagged in three retros, and front-loaded into 6.3. The Project Lead chose Option 1 (truly self-contained: remove the bootstrap, prove publish bundles the runtime). The architecture even carried a *wrong claim* ("Bootstrap finds the bundled runtime") that A32 corrected. Fixed in `5ea5d7e`. **Everyone assumed that was the install blocker.**

2. **The real crash, hiding behind it (`e6f3b20`).** With the bootstrap contradiction resolved, the *build-output* exe ran — but the *published/installed* exe still crashed at the first window with `Microsoft.UI.Xaml.dll 0xc000027b`, no diagnostic, `MainWindowHandle 0`. Root cause: **unpackaged WinUI `dotnet publish` silently drops `resources.pri` / `.xbf` / `Assets`** (the build output has them; publish doesn't). Fixed by a `_CopyWinUIResourcesToPublish` MSBuild target. This is now durable knowledge (`winui-publish-drops-resources`).

The lesson: the *named, tracked* blocker was real but was not the whole story; the *publish ≠ build* gap was a second, undiagnosed-until-you-actually-install-it defect of exactly the WinUI-runtime-reality class this project kept hitting. **A green build is not a runnable install.**

And then, even with a launching installed app, the installer *itself* had a defect no test models: the **"Preparing to Install" Restart-Manager hang** (`1dad11b`) — InnoSetup's `CloseApplicationsFilter` scanned too broadly and the RM scan hung; narrowed to `ohSpy.App.exe`. Three real-machine integration defects (bootstrap, publish-resources, RM hang), zero of them catchable by the unit suite.

- **Refinements** (the majority): return-type symmetry, analyzer exemptions, file-sink location, DI-cycle discipline, allocation-measurement technique. The spec got *more correct* as implementation taught it things.

The honest read: the *refinement* amendments are the spec-driven loop working as designed (lean spec, learn through implementation, amend with paper trail). The *reality-driven* corrections (A30/A31/A32/A33/A34) cluster around exactly the things AI-from-spec is blind to — real hardware shapes, real user perception, real machines, real networks. The amendment ledger is, in effect, a map of where spec-driven AI development is strong vs blind.

## Part 3 — The headline durable lesson: the test-vs-reality gap

This is the most important thing the project has to teach, and it is consistent across all six epics. **A large, green test suite repeatedly failed to catch defects that manual smoke, real devices, real networks, and clean machines surfaced.** Every single epic's headline "what didn't go well" is an instance of it:

| Epic | Green at the time | What the suite could not see | Surfaced by |
|---|---:|---|---|
| 1 | 126 | The chaos hook was a silent no-op (MSTest filter in xUnit) — "trivially passing" | Running it against a known-bad case |
| 2 | 313 | The device tree never expanded — WinUI TreeView leaves container `DataContext` null; VM tests set `IsExpanded` directly so they "proved" expansion | First real UI run (after 4 reviews) |
| 3 | 356 | `RPC_E_WRONGTHREAD` hard crash — WinUI has no `SynchronizationContext`; the **test double** (`InlineUiDispatcher`) ran `Post` inline and masked the missing marshalling | First real invoke (smoke-per-story) |
| 4 | 515 | **UDN-as-`Guid` design bug** — every fixture used an RFC-4122 UUID; the first real Linn device (non-conforming UDN) silently vanished | First real device on the live network |
| 5 | 537 | Diagnostics viewer functionally dead on screen — `ItemsRepeater` leaves realized `DataContext` null (severity colour + filter both no-op) | Adversarial App-XAML review + smoke |
| 6 | 574 | (a) install crashes — bootstrap contradiction, then publish-drops-`resources.pri`; (b) installer RM hang; (c) **no inferred-byebye expiry**; (d) **no network-change detection** | Clean-machine install + real-world use |

The pattern is unmistakable and falls into two buckets:

1. **WinUI runtime/render reality.** Five distinct, durable gotchas (`winui-treeview-datacontext-null`, `winui-no-struct-databinding`, `winui-no-synccontext-marshal-vm`, `winui-window-root-itemsrepeater-binding`, `winui-publish-drops-resources`). The headless Core suite *structurally cannot* see WinUI rendering, threading, or publish-time resource packaging. Worse, the convenient **test double itself** (`InlineUiDispatcher`) was a blind spot — it masked the very marshalling bug it was meant to stand in for.

2. **Real-hardware / real-network / real-machine integration.** The UDN-as-Guid design bug (RFC-4122 "SHOULD" vs a real non-conforming UDN), the no-byebye expiry, the network-change blindness, and all three install defects. No unit test owns a real power switch, two physical networks, or a clean Win11 box.

**What this reveals about spec-driven AI development:**

- **Where it is strong:** Core domain logic, structured decomposition, test coverage of *specified* behaviour, async/threading discipline *where the contract is explicit*, refactors against a typed boundary, and — critically — *catching its own spec's drift* (`create-story` reconciliation found 3 identity sites even the corrective change-proposal missed). The Core stack is excellent: 574 tests, 0/0 warnings, a clean Pattern-2 boundary that never leaked WinUI in 27 stories.
- **Where it is blind:** anything whose truth lives in the *runtime* and not the *spec* — GUI rendering and z-order, the absence of a `SynchronizationContext`, publish-vs-build packaging, the shape of real hardware identifiers, devices that misbehave by *omission* (no byebye), the host's physical network, and the target machine's clean state. AI generated from a spec faithfully implements the spec — including the spec's wrong assumptions (UDN-as-Guid, "Bootstrap finds the bundled runtime") — and tests generated alongside encode the *same* assumptions, so they go green on the flaw.

The durable countermeasure the project converged on — and which **must** carry into every future Claude+BMad project that has a GUI or real-hardware/real-network/real-machine surface — is **manual smoke per UI-touching story, on the real thing, before review/done, against the largest/most complex real target, with a clean-machine install dry-run as a release gate.** This was Epic 2's hardest-won lesson (`smoke-per-ui-story`), and every epic afterward proves it pays: Epic 3's smoke caught a process crash 356 green tests missed; Epic 5's diagnostics tool found an Epic-2 bug the instant it rendered; Epic 6's install dry-run and real-world use found four field defects 574 green tests missed.

A second-order lesson: **"trivially passing" / a hardcoded assertion is a red flag, not a green one** — A18 (Epic 1) and the 6.2 hardcoded 8-hr asserts (Epic 6) are the same class, a full project apart. The Sonnet review eventually learned to *hunt* for it.

## Part 4 — The BMad process itself (honest assessment)

**What clearly worked:**

- **Fresh-context-per-story.** Cost: one extra context per story for create-story and one for review; token-trivial against implementation. Benefit: every story re-derived its understanding from the shipped code, which is exactly what caught the recurring "epic prose diverges from reality" drift (5 stale statements corrected in 5.3 alone, 3 identity sites in 2-10) *before* dev — zero rework cycles in the entire project. The fresh context is a feature: it prevents an accumulating, increasingly-wrong mental model.
- **Sonnet-reviews-Opus's-code (different model, fresh context).** Did real work every single epic — not rubber-stamping. It verified claims against generated `.g.cs` (2.9), ran both chaos-filter forms live (1.6), found a genuine malformed-2xx correctness bug (3.1), a TOCTOU (4.2), the dead `ItemsRepeater` bindings (5.1), and the hardcoded soak assertions (6.2). An independent reviewer model is a cheap, high-yield gate.
- **The pre-commit chaos hook in lieu of CI.** ~5 s, caught `.Result`/`.Wait()` regressions and NFR invariants, 0 bypasses in 60 commits. For a single-developer, no-CI project this was the right call — *once A18 was fixed*. (The A18 episode is the cautionary footnote: an unverified hook is worse than no hook because it gives false confidence.)
- **Correct-course for the corrective block.** When real-world defects (UDN, expiry, network-change) appeared on a *closed* epic, the `correct-course` workflow produced a sprint-change-proposal, authored the new FR + amendment, and ran the corrective stories *without re-opening the epic status*. Clean, auditable, and it kept the epic ledger honest. The 2-10 precedent was reused three times.
- **Architecture amendments with provenance.** The single most tellable artefact of the L&L. The doc got *more correct* over time, every refinement defensible, every correction traced to a story and commit.

**What was friction or limitation:**

- **The methodology cannot, by construction, generate the WinUI-runtime and real-world knowledge it most needed.** Every WinUI gotcha and every field defect was learned *the hard way, in smoke or in the field*, then written into durable memory so the *next* story wouldn't relearn it. That's the loop working — but it means the value of the gate (manual smoke) is what saved the quality bars, not the spec or the tests. A future project should treat the durable-memory WinUI hazard list as a *pre-loaded* checklist, not something to rediscover.
- **Thick spec skeletons are fragile.** Epic 1 found 5 real bugs in > 50-line inline C# skeletons. Lean specs (intent + interface + edge rules + small examples) shipped cleaner. The action item (compile-the-skeleton before locking) was only partially adopted.
- **Single-device test network was a recurring bottleneck** through Epics 3–4 until the 5.2 adapter switch turned the Linn-DS network into a first-class capability. Verification tooling, not implementation, was the binding constraint for a stretch.
- **Deferred smoke compounds.** The one time the team batched UI smokes to epic close (Epic 2), a tree bug hid past 4 reviews and 313 tests. Never repeated after the `smoke-per-ui-story` rule.

## Part 5 — Verdict on the L&L question: did Claude + BMad beat the spec-kit UpnpSpy?

**Yes — clearly, on the dimensions that were declared non-negotiable, with honest caveats.**

The comparison is unusually clean: same author, same problem statement, same domain. The prior `UpnpSpy` (Claude + spec-kit) is recorded in project memory as **"adequate but slow, with unnecessary full-screen repaints."** ohSpy's three non-negotiable quality bars were **reliability, performance, UI polish** — and the prior tool's noted weaknesses (slow, full-screen repaints) are *performance and UI-polish* failures specifically.

ohSpy's evidence against those bars:
- **Performance:** virtualised tree / log / diagnostics / event lists (no full-screen repaints — the prior tool's exact failing); cold-large-SCPD 21 ms vs a 2 s budget; sustained ≥ 20 adv/s with 0 stalls; a 1-hr soak with max dispatch gap 177 ms and no leak; every SC-* budget walked and met on the real LAN.
- **Reliability:** 574 green tests, a typed timeout-discipline facade that makes the prior tool's failure mode a type-system property, a three-level cancellation hierarchy, hardening on the inbound GENA host (conn cap / slowloris / oversize), a 1-hr no-crash/no-stall soak, *and* — the strongest reliability signal — the project found and fixed its own real-world reliability holes (no-byebye expiry, network-change) as a disciplined corrective block before release rather than shipping them.
- **UI polish:** five WinUI render hazards hunted down and codified; a dedicated manual-verification story (6.1) with a PASS matrix; A31 z-order tuned *by use*; polish defects (phantom chevron, popup-behind) caught by eyeballs and fixed.

But the more important L&L claim is about the **methodology and the journey**, and here the verdict is strongest. BMad produced something spec-kit did not: an **auditable provenance trail** — brief → PRD → architecture (34 amendments, each traced to a story/commit) → 27 stories + a corrective block → fresh-context create/dev/review per story → manual smoke → v1.0.0 — with **zero rework cycles** and a living architecture document that got *more correct* over time. The story of *how* it was built (the retros, the amendment ledger, the test-vs-reality lessons) is itself a teachable artefact. That is the pitch.

**The honest caveats (the L&L should state these, not hide them):**
- The win was **not** "the spec was right and the AI executed it." The spec was wrong in load-bearing ways (UDN-as-Guid, the bootstrap claim) and the AI faithfully implemented the wrong spec — *and the tests went green on the flaws.* What rescued the quality bars was the **human-in-the-loop manual smoke gate** and the **independent-model review**, not the spec or the generated tests.
- The decisive differentiator over spec-kit was therefore **process discipline** (fresh-context reconciliation, smoke-per-ui-story, Sonnet review, correct-course, the chaos hook) more than raw generation. BMad's structure is what made that discipline cheap and repeatable.
- A no-CI, single-developer, manual-smoke-gated process scaled fine *for this project*; it would need an automated UI/integration tier (and a real CI) to scale to a team or to a tool without a single engineer who can eyeball every smoke.

Net: **Claude + BMad delivered a tool that meets all three non-negotiable bars and beats the prior tool on its known weaknesses, plus a methodology trail spec-kit didn't produce — provided you read "the methodology" as the human-gated loop, not unattended spec-to-code.**

## Part 6 — Action items & takeaways for future Claude + BMad projects

These are forward-looking, specific, owned, and free of time estimates (per workflow rule).

### Process

| ID | Action | Owner | Trigger |
|---|---|---|---|
| **N** | **Pre-load the WinUI render-hazard checklist into every GUI story's create-story.** The five durable memories (`winui-treeview-datacontext-null`, `winui-no-struct-databinding`, `winui-no-synccontext-marshal-vm`, `winui-window-root-itemsrepeater-binding`, `winui-publish-drops-resources`) are the *known* blind spots — make them a standing "have you considered" block in any story touching XAML, a window, a binding, or publish/packaging, so the next project doesn't re-pay the smoke cost to rediscover them. | spec author | any GUI / window / binding / packaging story in a WinUI (or any GUI) project |
| **O** | **A clean-machine install dry-run is a release gate, not a story task — and it must run the *published/installed* artefact, never the build-output exe.** The build-output exe ran while the installed one crashed (publish-drops-resources). Bake "publish, install on a clean box, launch, verify the first window renders + diagnostics write + uninstall behaves" into the release checklist of any unpackaged-desktop project. | project lead | every desktop release |
| **P** | **Treat "trivially passing" / hardcoded assertions as defects until proven by a known-bad case.** A18 (Epic 1) and the 6.2 hardcoded 8-hr asserts (Epic 6) are the same class. Any new test-infra or soak/perf assertion must be demonstrated to *fail* against an injected bad state before it's trusted. Make the reviewer hunt for it explicitly. | spec author / reviewer | any test-infra, soak, perf-budget, or "verify it fires" AC |
| **Q** | **For opaque-string / external-format domain values, model as string and fixture with a real non-conforming value from the target hardware.** The UDN-as-Guid bug (A30) survived 515 RFC-4122-shaped tests because no fixture used a real non-conforming UDN. Any field whose format is a spec "SHOULD" (not "MUST") gets ≥ 1 real-hardware non-conforming fixture. (Carry-forward of Epic-4 Action K, now generalised.) | spec author / dev | any domain field with a spec "SHOULD" format |
| **R** | **Model failure-by-omission in fakes, not just failure-by-commission.** The no-byebye expiry hole (FR-056) existed because every fake either stayed alive or *sent* byebye — none modelled a device that vanishes *silently*. Test farms must include devices that misbehave by doing nothing (no byebye, no response, disappearing mid-session), and the network must be modelled as changeable (FR-057). | dev / test author | any discovery / liveness / network-dependent feature |

### Standing policies confirmed for re-use (do not drop)

- **smoke-per-ui-story** — manual smoke on the real app/target for every UI-touching story before review/done. The single most valuable gate in the project.
- **L** — smoke against the largest/most complex real target, not the first that appears.
- **H** — one `DeferredUiDispatcher` (or equivalent off-thread) marshalling-guard per async VM path; never trust the inline convenience double.
- **Independent-model code review, fresh context, every story.** Cheap; caught real bugs in every epic.
- **`create-story` reconciliation against shipped code** — keeps the spec honest; catches the methodology's own drift.
- **`correct-course` for post-close defects** as a corrective block that doesn't re-open the closed epic.
- **Pre-commit chaos hook in lieu of CI** for single-dev no-CI projects — *but verify the hook fires against a known-bad case before trusting it.*

## Part 8 — Key takeaways (project closeout)

1. **The test-vs-reality gap is the durable lesson.** A maximally-green suite (574/2) never caught a single one of the headline defects across six epics — they were all surfaced by manual smoke, real devices, real networks, or a clean machine. Spec-driven AI is strong on Core logic, structured decomposition, and specified behaviour; it is blind to GUI runtime/render reality and real-hardware/real-network/real-machine integration. **The human-gated manual smoke is what protected the quality bars.**
2. **Tests can encode the spec's wrong assumptions and go green on the flaw.** UDN-as-Guid passed 515 tests; "Bootstrap finds the bundled runtime" was a wrong architecture claim faithfully implemented. Independent review + real-target smoke + non-conforming fixtures are the antidote.
3. **A green build is not a runnable install.** Publish drops resources the build keeps; the installer can hang; the named blocker can hide a deeper one. Make clean-machine install of the *published* artefact a release gate.
4. **Retros compounded.** Action items A→M were applied, validated, or consciously superseded epic over epic; smoke-per-ui-story (E) paid for itself in every subsequent epic. Accountability across retros is itself a methodology win.
5. **The architecture amendment ledger (A1→A34) is the L&L's best artefact** — the spec got *more correct* over time, with provenance, and the reality-driven corrections map exactly onto where AI-from-spec is blind.
6. **Verdict on the L&L:** Claude + BMad beat the spec-kit prior tool on its known weaknesses (slow, full-screen repaints) and on methodology trail — *because of the human-gated, independent-reviewed, reconcile-against-reality process discipline*, not because the spec was right or the generation was unattended. State that honestly; it is the more useful and more credible pitch.

Epic 6 is closed and **ohSpy has shipped v1.0.0.** The verification-only epic did its real job — it (and real-world use) found the field defects 574 green tests could not: two reliability holes (FR-056/FR-057, fixed as a corrective block) and a two-layer install blocker plus an installer hang (all fixed before release). All three non-negotiable quality bars — reliability, performance, UI polish — are met and evidenced on real Linn/OpenHome hardware and a clean Win11 box. The methodology trail (brief → PRD → architecture A1–A34 → 27 stories + corrective block → per-story create/dev/Sonnet-review/smoke → six retros → this closeout) is intact and tellable end to end.

The single durable lesson to carry to the next Claude + BMad project: **build the Core with the spec, but trust the screen, the hardware, the network, and the clean machine — gated by a human — over the green checkmark.**
