## What went well

### Winston (Architect): every dev-story agent caught real defects in spec skeletons

The most striking pattern: spec skeletons containing > 50 lines of C# scaffolding consistently shipped with bugs that the dev agent caught at implementation time. The adversarial create-story review caught some upfront; the dev agents caught the rest:

- **Story 1.4** — `while (reader.Read())` double-advanced after `ReadElementContentAsStringAsync` (which already advances past end tag). Net effect would have been every other sibling element silently dropped. Fixed via an `advanced` flag in every reader.
- **Story 1.5** — `RotateToTodayAsync` would have infinite-looped (reopens already-full today's file → triggers another rotation → forever). Fixed via sequenced-suffix rename pattern.
- **Story 1.5** — `PruneOldFiles` off-by-one — retained `MaxRetainedFiles` instead of `MaxRetainedFiles - 1`, transiently exceeding the 8-file / 16 MB ceiling. Fixed.
- **Story 1.6** — `ResponseHeadersRead` vs `Body.FlushAsync` semantic confusion in the `HangAfter200Ok` Kestrel handler. Fixed via `Response.StartAsync` (canonical Kestrel API).
- **Story 1.6** — the A18 silent-no-op bug in `.githooks/pre-commit` filter syntax.

That's 5 real bugs caught and fixed by the dev agents that would have shipped if the loop weren't running. **This is the methodology delivering its promise.**

## What didn't go well — themes

### Murat: A18 — chaos hook silent-no-op for 5 stories

This is the most painful one to write down. We treated "filter matches 0 tests, exits 0" as "trivially-passing by design." It wasn't. The filter was MSTest TestProperty syntax pasted into an xUnit project. We didn't catch it for 5 stories because every dev-story agent and every reviewer accepted "chaos suite is empty, hook trivially passes" as the expected state.

**Root cause:** copy-paste from a TestProperty-syntax example into a Trait-syntax project, with no live verification.

**Lesson:** "trivially passing" is a red flag, not a green one. Any test infrastructure that's passing trivially should be regarded as untrusted until proven by running it against a known-bad scenario. Story 1.6's manual Task 9 smokes (revert ResponseHeadersRead / add `.Wait()` and observe failure) are the canonical pattern.

### Winston: spec-skeleton C# defects pattern

Stories 1.4, 1.5, and 1.6 all had defects in C# skeleton code authored into the story specs. Five real bugs across three stories.

**Pattern:** when story specs contain more than ~50 lines of skeleton C#, defects are likely.

**Lesson:** lean specs (intent + interface + edge-case rules + small examples) ship cleaner than thick specs (full reference impls). Future story specs should either:
- Constrain skeleton C# to ≤ 50 lines per task (let the dev agent compose from primitives), OR
- Pass thicker skeletons through a compile-it sanity check before locking the spec.

Both options surface in the action items below.

### John: FluentAssertions 8.0.0 commercial-license surprise

Pinned during Story 1.1; the Xceed licence warning appeared on every test run for 5 stories before Story 1.6's code-review surfaced it as deferred work.

**Lesson:** when pinning a new package version in `Directory.Packages.props`, check the LICENSE file too, not just compatibility.

**Resolution:** downgrade to FluentAssertions 7.2.0 (last MIT-licensed). Applied as part of this retrospective.

### Amelia: `Microsoft.Extensions.*` package management was a surprise three times

- Story 1.3 needed me to think about whether `Microsoft.Extensions.Options` was transitively available (it wasn't; needed explicit Core PackageReference).
- Story 1.5 hit the App-side `Microsoft.Extensions.Logging` gap (needed because `services.AddLogging()` extension lives in that assembly, not in `DependencyInjection`).
- Story 1.6 triggered NU1510 against three packages because the new `FrameworkReference` provided them transitively (A16).

**Lesson:** `PackageReference + FrameworkReference + transitive-pin` interactions deserve their own checklist. Future stories adding any new `Microsoft.Extensions.*` or framework reference should walk through:
1. Is the type accessible from the assembly that uses it? (Add `PackageReference` if not.)
2. Does the framework/transitive-pin already provide it? (Remove duplicate `PackageReference` if so — NU1510.)
3. Is the licence still compatible? (Check the new package's LICENSE.)

## Key insights worth capturing for L&L deliverable

1. **The adversarial create-story review is load-bearing.** Across 6 stories it caught: missing `InternalsVisibleTo`, version skews, double-advance bugs, BuildInstaller path mismatches, allocation-elision sequencing errors. Average: 4–5 critical issues per story. Skip it once and you ship broken specs.

2. **Spec-skeleton C# longer than 50 lines is fragile.** 5 real bugs across 6 stories came from copy-paste errors in spec skeletons.

3. **Architecture amendments are a feature, not a failure.** 9 amendments across 6 stories. Each captured a real gap; each had clean provenance; each propagated to subsequent stories. **This is the methodology's actual value proposition.**

4. **"Trivially passing" is a red flag, not a green one.** A18's "chaos hook matches 0 tests" looked like the spec said it would. It wasn't.

5. **The independent-LLM code-review pattern works.** Opus implementing, Sonnet reviewing, fresh context each time. Every story produced either an APPROVED or APPROVED-WITH-MINOR-FIXES verdict with non-trivial substantive findings.

6. **"No production code changes" is achievable for test-infrastructure stories.** Story 1.6 added ~10 tests + 1 hook fix with zero src/ edits.

7. **The dev-story → code-review → architecture-amendment loop closes the spec ↔ code gap with auditable provenance.** Stories 1.2 and 1.4 had zero amendments — clean implementations. Stories 1.1, 1.3, 1.5, 1.6 produced 2–3 amendments each. The split is data, not failure.
