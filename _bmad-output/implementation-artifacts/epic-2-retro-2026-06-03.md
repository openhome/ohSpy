## What went well

- **The Opus-implements / Sonnet-reviews / fresh-context pattern held for a second epic.** Specs tightened over the epic: the last three stories (2.7/2.8/2.9) all returned APPROVED with **0 patches**. The 2.9 review did genuine work — it *verified* the dev's CS1503 converter claim against the generated `.g.cs` rather than accepting it.
- **Seam discipline kept Core pure.** Every unmockable platform edge got an interface — `IUriLauncher` over `Process.Start`, `IPropertiesLauncher` over window construction, `IWindowOwnershipManager` over Win32 `SetWindowLongPtr`. `CoreAppBoundaryTests` stayed at 4 green all epic; `PropertiesViewModel` is fully unit-tested in Core while the windowing/XAML lives App-side.
- **Cross-story reuse worked as designed.** 2.9's Properties hyperlinks reused 2.8's `BrowserLaunch` whitelist verbatim — no second browser-open path. The `NodeServices` bundle absorbed each new node-VM dependency (`IUriLauncher`, then `IPropertiesLauncher`) without re-plumbing the tree.
- **Honest gap-flagging over faking.** 2.9 surfaced that `DeviceDescription` flattens embedded devices (FR-053), so the spec's "EmbeddedDevices" section has no data source — documented as a known gap with a placeholder, not faked.
- **The first Win32 interop landed cleanly.** `[LibraryImport]` source-gen + `GWLP_HWNDPARENT` ownership worked first time; the one surprise (`AllowUnsafeBlocks` required by SYSLIB1062) was caught by the dev and accepted in review.

## What didn't — the headline lesson

**Deferred manual smokes hid a real bug that unit tests structurally could not catch.** Stories 2.5/2.6 wired the device tree; their unit tests set `IsExpanded = true` *directly*, so they passed and "proved" expansion worked. But two things were both broken in the UI:

1. The node VM's `IsExpanded` (which drives the Story 2.6 lazy build) was **never wired to the TreeView's expand state**.
2. **WinUI 3 TreeView leaves each generated `TreeViewItem`'s `DataContext` null** (confirmed at runtime: `container.Content` is the node VM, `container.DataContext` is `null`), so the textbook `ItemContainerStyle` `{Binding Children}` resolved to nothing — no children, no chevron — regardless of the binding expression or `ItemTemplate`-vs-selector.

The net effect: discovered devices rendered, but **nothing could be expanded** — no services, no actions, no chevrons. It survived two stories, four code reviews, and 313 green tests, and only fell out on the first real UI run. The fix (commit `4d380f8`) assigns each container's `ItemsSource` in code as rows realize (via the tree's `LayoutUpdated`), plus `OnTreeExpanding` for the lazy load — the only mechanism that works given the null `DataContext`.

This is **exactly the failure mode Epic 1's Action Item B warned about** — "trivially passing? prove it's actually wired." We logged that lesson for *test-infra* (does the hook fire?) and did not extend it to *UI-binding* ACs. The debt also **compounded**: 2.6, 2.7, 2.8, and 2.9 all deferred their manual smokes (headless dev env), so four stories' worth of UI verification came due at once at epic close — which is when the bug finally surfaced.

The diagnostic method that cracked it is worth keeping: temporary `Warning` diagnostics written to the app's own rolling log file (readable post-run), plus a direct SSDP M-SEARCH + HTTP fetch of the live device to prove the data was present. That turned a blind "it doesn't work" into a precise "VM builds N children, container DataContext is null" in two iterations.

**Concrete carry-forwards for Story 3.2:**

1. **Reuse the 2.9 popup seam shape.** 3.2's invocation popup should mirror `IPropertiesLauncher`/`PropertiesLauncher` (a Core launcher interface + App impl doing factory → `new XxxWindow` → `Activate()` → `Adopt(window, shell)`), and reuse the Pattern-7 `Func<…, XxxViewModel>` factory + `ShellWindow` wiring from `App.OnLaunched`. The pattern is now battle-tested.
2. **Action double-click rides on the tree fix.** The tree's `OnTreeDoubleTapped` currently toggles expansion for *device/service* nodes; action nodes are leaves and fall through (no-op). Story 3.2's "double-click action → invocation popup" extends that same handler (or wires the action node) — and any new tree/popup binding must assume the **container `DataContext` is null** (set `ItemsSource`/handle events in code, per the tree fix), not rely on `{Binding …}`.
3. **Smoke 3.2 in-app per Action Item E** — the invocation flow (build SOAP, POST, render outputs / fault) and the popup ownership are UI-heavy; verify on a live device (the Sky Hub WFADevice `WFAWLANConfig` service is a handy real target) before marking the story done.

## Key takeaways

1. **A green VM test does not prove the UI is wired.** Extend "trivially passing? prove it's wired" from test-infra to every UI-binding AC, and smoke UI stories as you go.
2. **WinUI 3 TreeView databinding leaves the container `DataContext` null** — assign child `ItemsSource` / handle expand in code; the declarative `{Binding Children}` is a trap here.
3. **The seam-per-platform-edge discipline scales** — three new seams this epic, Core stayed boundary-clean, and the popup seam is directly reusable by Epic 3.
4. **Deferred manual smoke compounds** — four stories' UI verification came due at once and that's where the bug hid. Per-story smoke (Action Item E) breaks the compounding.
